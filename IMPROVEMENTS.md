# Улучшения проекта обновления отчёта

## Уже реализовано

- Отдельный локальный проект `C:\projects\opros-site-updater` на ветке `main`.
- Обновление `index.html` из read-only ресурса `\\PC-BA2\KB-ARM-survey` без изменения исходных файлов.
- Сохранены существующие вкладки, фильтры, поиск, сортировка и исключения сайта.
- Детерминированный пересчёт трёх сценариев с дедупликацией повторных файлов одной сессии.
- Проверка итоговых счётчиков и отказ от записи при противоречивых данных.
- Инкрементальный индекс источника: неизменившиеся Markdown-файлы повторно не читаются по сети.
- Автотесты Python и отдельная проверка встроенного JavaScript и контракта фильтров.
- Безопасный цикл обновления: чистое рабочее дерево, `git pull --ff-only`, пересчёт, тесты и локальный коммит только при наличии изменений.
- Ежедневная задача Windows `Opros-Site-Update-0850` на 08:50 для пользователя с доступом к сетевой папке.
- Раздельные журналы штатного выполнения и ошибок запуска PowerShell.
- Локальные индекс, временные файлы и журналы исключены из Git.
- Граф проекта Graphify для быстрого поиска связей между файлами и проверок изменений.

## Обязательные ближайшие улучшения

1. **Закрыть доступ к данным.** Владелец или администратор должен перевести репозиторий в Private. Текущая учётная запись имеет доступ к коду, но GitHub не разрешает ей менять параметры репозитория.
2. **Отдельно определить доступ к сайту.** Private-репозиторий сам по себе не гарантирует, что GitHub Pages станет приватным. После смены видимости нужно проверить Pages и либо отключить публичную публикацию, либо использовать доступный для организации режим с ограничением доступа.
3. **Отправить подготовленные коммиты только после закрытия репозитория.** До этого новые ФИО и статистику в публичный GitHub не публиковать.
4. **Включить безопасный автопуш отдельным решением.** Ежедневная задача сейчас делает только локальные коммиты. Автопуш следует включать после смены видимости и проверки неинтерактивной авторизации; при расхождении веток он должен останавливаться, а не выполнять принудительную перезапись.

## Надёжность и наблюдаемость

- Добавить lock-файл или mutex, чтобы два запуска не обрабатывали источник одновременно.
- Настроить повтор запуска задачи при временной недоступности сети и `StartWhenAvailable` после пропущенного запуска.
- Добавить ограничение времени выполнения и явный код причины ошибки для каждого этапа.
- Ввести ротацию журналов по размеру или сроку хранения.
- Сохранять компактный `status.json`: время последнего успеха, версия коммита, число файлов, сессий и ошибок.
- Добавить уведомление только при сбое или отсутствии успешного обновления дольше суток.
- Перед автопушем создавать проверяемый тег или хранить один предыдущий рабочий снимок для быстрого отката.
- Периодически запускать браузерный smoke-тест опубликованной страницы: загрузка, вкладки, фильтры и отсутствие JavaScript-ошибок.

## Качество данных

- Подключить утверждённый кадровый реестр как единственный источник состава сотрудников вместо наследования списка из прежнего `index.html`.
- Вынести исправления написания ФИО и известные соответствия в версионируемую таблицу правил без персональных данных в логах.
- Не добавлять неоднозначное совпадение автоматически: помещать его в отдельный отчёт на проверку.
- Валидировать обязательные поля frontmatter и помещать некорректные файлы в список исключений с понятной причиной.
- Хранить в диагностике только агрегаты и идентификаторы файлов; не писать ФИО и содержимое интервью в журналы.
- Добавить контроль резких изменений: необычное падение или рост числа сотрудников, сессий либо завершённых сценариев должен останавливать публикацию.

## Производительность

- Сохранить текущий инкрементальный индекс как основной механизм: он уже исключает повторное чтение неизменившихся файлов по SMB.
- Перейти на SQLite только при существенном росте объёма или необходимости сложной истории; для текущего размера JSON-индекс проще и быстрее в сопровождении.
- Обновлять только блок данных и метаданные снимка, не пересобирать неизменную разметку и фильтры.
- Замерять длительность чтения, разбора, тестов и Git-операций отдельно, чтобы оптимизировать фактическое узкое место.

## Безопасность сопровождения

- Ограничить список GitHub collaborators минимально необходимыми ролями и включить защиту `main` после настройки автоматизации.
- Не хранить токены, пароли и сетевые учётные данные в репозитории, скриптах, планировщике и журналах.
- Не использовать GitHub-hosted Actions для чтения `\\PC-BA2`: облачный runner не имеет доступа к локальному SMB. Для этого источника подходит текущая Windows-задача или изолированный self-hosted runner.
- Запретить `push --force` в автоматическом сценарии; допустимы только fast-forward обновления после успешных проверок.

## Предлагаемый порядок

1. Владелец выдаёт текущей учётной записи Admin либо сам переводит `adelinaatp-source/opros` в Private.
2. Проверяем реальную видимость GitHub Pages и закрываем публичный доступ, если он сохранился.
3. Отправляем подготовленные локальные коммиты и проверяем удалённый `main`.
4. После отдельного разрешения включаем автопуш и уведомление о сбоях.
5. Подключаем утверждённый кадровый реестр и правила разбора неоднозначных ФИО.
